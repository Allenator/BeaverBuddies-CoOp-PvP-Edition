# Tests

The library and runner for scenarios that play the game, and the checks that need no game. Mods built on BeaverBuddies use them too: Timber Empires' `Tools/Tests` has its own scenarios and runs this runner on them.

## Fast checks, no game

    Tools/Tests/fast.sh

Checks that every translation has English's keys, once each and in order (`translations.py`), then builds the mod twice, into a scratch folder so the Mods folder isn't touched: the Steam build, and the one without Steam networking and matchmaking (`-p:Steam=false`), to catch code that should compile either way. A few seconds.

## Game scenarios

    Tools/Tests/run.sh [--no-build] [--list] [name...]

Builds BeaverBuddies first (skipped when nothing changed since the last build: no file edited, added, removed or put back), then runs each script in `scenarios/` (and in the folders of `BB_SCENARIOS`, a colon-separated list) on two windowed copies of Timberborn, a host and a guest, driven through the test harness (`BeaverBuddies/DevTools/TestHarness.cs`, only active with the `BB_INSTANCE` environment variable): each copy takes commands from a file and logs what it did. With names, only the scenarios whose file name contains one. The report is `report.md` in `$BB_TEST_DIR` (`$TMPDIR/bb-tests` by default), with the copies' logs and the scenarios' screenshots. The exit code is 1 if a check failed.

- `bb-only`: with Timber Empires switched off, the New Game page has no mode column, and a hosted game starts as Co-op and stays in sync.
A scenario past `BB_SCENARIO_TIMEOUT` (600 s) fails and is stopped, and the whole run has a limit too, `BB_RUN_TIMEOUT` (1800 s, 0 for none): past it everything is killed, the copies closed, and it says so and posts a notification.

A desync during a scenario stops it there and fails it ("stays in sync", with the log lines that show why) and posts a notification, so a run never sits waiting after the host has resynced. A scenario that resyncs on purpose has a `BB_EXPECT_DESYNC` comment and is left alone. Game logic that went out as a player's action fails a scenario too, as it ends: the tick guard's `[SyncGuard]` line in either copy's log (see `ReplayEvent.InGameTick`). A scenario that trips the guard on purpose has a `BB_EXPECT_SYNC_GUARD` comment.

- `sync-rules`: the tick guard reports a synced method the game's own tick calls (a lever pinned from inside a tick, `lever x y z tickpin`), in that copy only, and not a player's own setting between ticks, nor a workplace taking its district's worker type from inside a tick (`workertick x y z`), which is game logic and isn't sent; a name typed with spaces around it is trimmed for everyone, as the game does alone (`rename x y z text`, `_` for a space, and `name x y z`).

- `cosmetics`: each choice made on one side and the same on both: a banner's and a tail painter's image picked through the picker's own button handler (`decalpick x y z category id`), an image flipped (`flip`), a light customized and colored from its field and from a preset (`lightcustomize`, `lightcolor`, `lightpreset`), an HTTP Lever colored from the HTTP API (`lever x y z httpcolor RRGGBB`) and a speaker's sound (`speaker x y z sound`). The host sees none of the custom files the guest has (`BB_HIDE_CUSTOM_HOST=1`; any copy can be given one, `BB_HIDE_CUSTOM_<COPY>`, since both copies share one Documents folder): it keeps their names anyway, shows or plays the default for them, and keeps them through Refresh (`decalrefresh category`) and a reload from its own save. The scenario puts its test files in Documents/Timberborn's Banners, Tails and Sounds and takes them out again; `decal`, `light`, `speaker`, `decals category`, `sounds` and `decaltools` say what a copy has.

- `desync-resync`: a desync reloads both copies from the host's save over the connection they already have, and they carry on in sync; the dialog after it opens Discord to report it, with tracing on saving the desync's trace next to Player.log first, and without tracing has a button of its own that turns tracing on for everyone, which every copy's screen then says.

- `trace-new-game`: with detailed logging on for both players, for the session as the desync dialog turns it on and by "Always trace", a hosted new game is traced from its first tick, not its load (which the host's new game and the guest's load from its save do differently), and doesn't read as a desync at once.

- `demolish-site`: placing and demolishing construction sites while builders work on them, 25 rounds, stays in sync.
- `demolish-tool`: each player demolishes a finished building with the demolish tool, and it goes for both copies.
- `builder-priority`: the builders' priority tool dragged over things that have that priority already, as before the desync of October 24, 2026. The game sets each again anyway, which moves a demolish job to the back of its priority's queue, the order builders take equally close jobs in. The guest marks the natural resources in a square near its start (`findresources x y r size min`, `markresources x0 y0 x1 y1 [gone]`; gone, with one more that's no longer there as it plays, which mustn't keep the rest from being marked), sets them to VeryHigh, and drags VeryHigh again over half of its rows (`priority x0 y0 x1 y1 Priority`), and both copies' queues (`demolishjobs`) have to be the same after each. Then the builders work for `BB_PRIORITY_SECONDS` (30), and the copies have to stay in sync.
- `autosaves`: a game hosted or joined autosaves as the Autosaves settings say (how often, how many kept), on the host and the guest alike, and an autosave that's due waits while the game is paused ("Skip autosaves while paused"); a game alone autosaves as the game does, every 10 minutes keeping 3, paused or not, but a co-op game opened alone (the Multiplayer settlement, where a guest saves) goes by the settings too, as the line above them in the settings says. Read from what the game's autosaver goes by (`autosaver`), whatever the player has picked.
- `host-leaves`: leaving says so. A guest that leaves tells the host, whose log has them leaving, not a connection that may have dropped; a host that leaves for the main menu tells the guest, which saves its own copy of the game (an autosave in the Multiplayer folder, which the runner puts back as it was) and is told the host left, rather than waiting on a host gone quiet.
- `state-check`: with tracing off, a guest whose walker positions alone part from the host's (`nudge`, a beaver moved a hair on that copy) sees it within a few ticks, from the hashes the host's heartbeat brings each tick, and has everyone resynced, the host's log saying what differed.
- `guest-pace`: at speed 7, where a tick (86 ms) is shorter than the 100 ms a guest keeps behind the host, the guest's own actions take about that cushion beyond the way there and back, as at speeds 1 to 3, not the 0.6 s of October 24, 2026, and it keeps that pace without stopping for the host's ticks. Its actions are its speed set to the speed it is, each a `[Latency]` line.
- `placement-check`: the preview a placement is checked on leaves the ground as it found it. The game's previews hide the ground a building sinks into (an Agora's middle, an Underground Pile) and keep water pumps' pipes from being drawn through their tiles; checks alone, fitting or not, on either copy, a guest's Agora, its construction site, the finished Agora (nine cells hidden, on both) and their demolitions are each followed by the harness's `cutouts` (the hidden cells, and what previews hold) on both copies.
- `district-preview`: a District Center the guest places with the building tool is in the guest's preview district map too, the map the tool checks a second one against, once the tool is put away. The pointer rests where it clicked while the host's placement comes back (`tool Template x y z click hover`, the preview held there each frame until the tool is put away with `defaulttool`), and `districts` lists each copy's maps (regular, instant, preview, with a preview's own district marked p), which have to be the same. Without `DistrictPreviewFix` the guest's preview map lost it, as a Windows guest's did before the crash of October 26, 2026.
- `event-order`: an event's handlers are called in the order they registered, on every copy, whatever came and went on one copy alone in the meantime (`eventchurn n` on the guest, n handlers registered and unregistered, as the batch control window's tabs do). Three goods piles (`pile x y z Good amount`, played on both) rest on three platforms, their handlers of a deletion (`eventorder`) have to be in the same order on both copies, and taking the platforms down keeps them in sync. Without `EventOrderFix` the guest's were in reverse, the cause of the platform desyncs of October 26, 2026.
- `zipline-limit`: a zipline tower takes no more connections than it has slots for. The guest and the host connect five pylons with the connection tool as a player does (`ziplineadd x y z`, the tower's Add connection button; `ziplinepick x y z`, a click with the tool; `ziplinetool`, the tower it connects from), and the tool goes on from the tower picked only while that one has a slot left, counting the connection still on its way, and is put away otherwise; then a connection from a full tower sent as is (`ziplineconnect x y z x2 y2 z2`) is refused by both copies. `ziplines` lists every tower's connections. Without the fix the tool stayed on the first tower and connected it a third and a fourth time, as on October 26, 2026.
- `lobby-wait`: a guest who waits a while (`BB_LOBBY_WAIT`, 30 s) in the lobby of a new game the host hasn't started sets its random state again as the host's first events play, which the game spent some of while it waited, and plays in sync (upstream's fix of October 25, 2026).
- `lobby-guest-leave`: a guest waiting in the lobby presses Cancel and leaves for the main menu, the host's box staying; then it joins the game once the host has started it, without the lobby's mark (it doesn't set its random state again there), and in sync.
- `load-in-coop`: the Load game box's Load, in a co-op game, loads nothing and says what to do instead (the host's Host game in that box, or the main menu). The host and then the guest press it on a save of the host's, opened from the game menu as a player does: neither loads, and both play on in sync. Before, the host's Load loaded its save alone, and its guest stood still waiting for ticks the host's new game had started again from 0, with no desync reported.
- `water-source`: a water source's dev mode boxes, Strength and Contamination, typed in by the guest with dev mode on (`devmode`, then `watersource x y z strength|contamination value`, the box's own field set; `watersource list` gives every source's values), change the source on both copies. Without the fix only the guest's changed, and the state hashes didn't see it: they cover the walkers, the entities ticked and the random state, not the water.
- `keep-awake`: a co-op game keeps the computer awake, hosted or joined, and lets go once it's left. Both copies hold a power assertion in the game (`keepawake` says how), which `pmset -g assertions` lists under the mod's name, and none is left at the main menu. Windows' execution state can only be checked in a player's game (`powercfg /requests`).
- `play-on`: after everyone reloads for a desync, the host's game plays on at the speed it was at once every player is back, with "Play on after a resync or a join" on (`modsetting PlayOnAfterReload 1`, one of BeaverBuddies' on/off settings set in the running copy), and waits paused for the host with it off, as by default. The game runs at speed 3 from the host's speed button (`play 3`) before each resync (`desync`), and the reload says it was from speed 3.
- `speed-throttle`: how much of the game's slowing of fast speeds in big colonies is lifted is the host's choice, for every player. The guest's own is the game's (`BB_THROTTLE_CLIENT`), the host lifts all of it and then half in the running copy (`throttle set 0|1|2`, never saved), and the guest follows each within a few seconds: `throttle 292`, the scale for the group's 292 characters, goes 0.40, 1.00, 0.70 on both copies.
- `tick-log`: a player's log has the tick's hash line every 100th tick, and the last 1000 ticks' lines are written out as they were at a desync, at a resync and as a crash's report is made. The copies log as a player's game does (`BB_TICKLOG_LIVE`; test copies otherwise log every tick, which the scenarios and helpers read): the 100th and 200th ticks' lines are there and the 150th's isn't, until the guest's desync writes out its last ticks, and the host's resync its own.
- `lever-spring`: a spring-return lever does in a Co-op game what it does alone. A pulse from the HTTP API's switch-on is on for one tick's automation and off by that tick's end, with only the switch-on sent as a player's action, and a lever's button held for 10 ticks, by the host or by the guest, keeps it on for them, sending only its press and let-go, while the other player letting go of it (as the pinned levers do when the pointer leaves one) does nothing. The button is one, shared by the host and the guest, and then by the guest and a third player (`Tools/FakePlayer` on the host's build): held by two, the lever stays on until the last of them lets go, whoever pressed first, two clicks at once switch it once, a let-go the third player sends as the guest (as a modified game could) is played as the third player's, so the guest's hold stands, and a lever the third player holds as they leave is let go of for them. Each copy logs the lever tick by tick (`DevTools/LeverWatch.cs`).
- `reload-leak`: three reloads in a row (a desync each, `BB_RELOADS` for more) leave the count of Unity objects flat, and the guest's managed heap after a full collection (`heap`) too: a game kept alive by references alone keeps Unity's count flat and grows the heap by the whole game. Needs logging on, which the harness runs with. Load times and a profile of each singleton's load are in the copies' logs, and with profiling (`BB_HITCH_MS`) each copy's leak finder lines; `cwtcheck` says whether a ConditionalWeakTable lets its keys go on this runtime, as the mod's caches count on. Both copies' loads have to be routed (the load routers on, not turned off by another patch), and `loadorder` says, for the events they route, whether the game's own order of their handlers has drifted from the order they registered, which they deliver in. Its copies write the pace line every 10 s (`BB_PACE_SECONDS`, 10 minutes in a player's game), which both have to, and log actions on one line.
- `reload-leak-save`: the same on a game the size of a real one. A copy of a saved game (`BB_LEAK_SAVE`, the newest in Multiplayer from before the run by default) is hosted from a settlement of the harness's own (`hostsave`), joined and reloaded `BB_RELOADS` times (3), `BB_RELOAD_GAP` seconds apart. After each, both copies say their heap (`heap`: after a full collection, Mono's used and reserved sizes, the collection count and the GC mode) and how many earlier games a full collection leaves alive (`scenes`, weak references to each game's event bus), and none may be left. `BB_LEAK_CLEAR` first clears a static known to hold the main menu (`leakclear`), and `BB_ROOTS` has the guest walk from every static field and live object to a game left alive (`roots`, minutes, off the main thread) and print the path. Mono's reserved heap never shrinks, so only `heap`'s collected size and `scenes` tell a kept game from the heap's high-water mark. It fails now and then today: an earlier game is sometimes kept (see the review of October 27, 2026).
- `chaos`: both copies shaken for `BB_CHAOS_SECONDS` (150 by default): frames that stall or run at other rates, messages that arrive late, and each player changing the speed, pausing, ticking once, placing and demolishing any building the game and the installed mods have, ordering troops, saving, and changing settings at random moments: builders' priorities over a square and demolish marks for them, a placed floodgate's height and synchronization, and a district's goods' distribution, often to what they are already, where the game's own method acts anyway. Then both copies exit to the main menu (only the host with the exit save) and play a second match without restarting, to catch state the last match or a save left behind; `BB_CHAOS_ROUNDS=1` skips that. `BB_CHAOS_LEVEL` is 1 to 3, `BB_CHAOS_SEED` the seed (the same seed does the same things, though not at the same instants), `BB_CHAOS_OFF` parts to leave out (`nospeed nodelete notroops noplace nonet nostall nosave nosettings`) to find which one a desync goes with. At the end it compares every entity of the two copies, and the ground each hides (`cutouts`).
- `webrtc-join`, `webrtc-list`, `quickmatch-worker`: with Steam networking off, as the Epic Games build plays. The guest joins by join code over WebRTC; finds a hosted game in Open matches (from its Worker lobby) and joins it from there; and the two play a whole Quick match through the Worker's lobbies, which the shared Steam account can't. They need the deployed Worker (`Signaling/`).
- `chaos-freeze`: the same, until the first desync; then nobody resyncs, both copies are stopped as they are, every entity is compared, and the host's analysis (which entities and water tiles differ, with their positions tick by tick and what each side's traces say about them) is printed. `BB_WATCH` is the id of an entity to keep an eye on.

A chaos run that finds nothing proves little; one that finds something is a bug with a recipe. Desyncs here come about one run in three or four unless fixed, so loop it.

A scenario that depends on the game's logging being on or off sets BeaverBuddies' "always trace" itself with `pref_set` (`lib.sh`), whatever this Mac has it at, and the player's own value is put back when the scenario ends.

Scenarios run the game at `BB_SPEED` (30 by default) while they wait on it.

Writing a scenario: see `lib.sh` (`start_match`, `send`, `wait_for`, `layout_of`, `shot`, the `expect_*` checks, and to play the game only as long as needed `run_ticks n` (n ticks at `BB_SPEED`, then paused), `run_until`, `run_until_log`, `pause_game`, `settle`, `answer` and `standing`, on the harness's `until`) and the scenarios here. The harness commands are the `case` labels of `TestHarness.cs`: `hostmatch Map Faction [game mode]`, `joinmatch`, `place`, `slots`, `speed` (sends the speed as an event), `play speed`, `speedkey speed` and `tickonce` (the speed buttons and keys, as a player presses them), `menu` (the game menu), `save`, `exitmenu [nosave]` (exit to main menu, with the exit save unless nosave), `click Button` (its `clicked` handlers and its click event, as a player's click runs both; a button a player couldn't click yet, not there, hidden, not laid out or under something else at its middle, is waited for as a player would, 5 s at most, and then the click fails saying why, the commands after it waiting their turn), `selectsave Settlement|Save name` (a save picked in the Load game box on top), `layout Element` (where an element of the panel on top sits), `desync [traced]`, `setfield Name value`, `gamesetting id value` and `matchoption id value` (this copy's picks for new games), `scrollend List`, `snap path`, `openmatches` and more. A mod can add its own: BeaverBuddies has the `te ...` command that passes its arguments to Timber Empires' probe.

What a run does to your Mac: it builds Game Modes (from the parent repo's submodule) and BeaverBuddies into a home of its own, `~/Library/Caches/TimberbornHomes/BeaverBuddies` (`BB_HOME`, named by `BB_HOME_NAME`), where everything else is a link to yours, and the copies play from there, so your Mods folder is never touched (`BB_HOME=$HOME` plays from it as before). Saves, settings and the game's preferences are still yours, through the links, which is why what follows about them holds. It refuses to start while your own Timberborn is running; the copies are windowed and play behind other windows, so the game's display settings go windowed and its "Run in background" on for the run (a copy alone, at the main menu say, stops otherwise when it isn't in front, since BeaverBuddies keeps the game playing only in multiplayer), and are put back after it (the next run restores them if one was killed); a scenario that switches a mod off moves its folder (a link, in the home) out of Mods and always puts it back. The copies share your settings, so BeaverBuddies' on/off settings the scenarios count on are set as they expect for each scenario (`BB_PINNED_SETTINGS` in `run.sh`: the defaults, but no welcome dialog), and yours are put back after it. The saves its games make go when it ends: the settlements made during the run named as the harness, Host new game and Quick match name them ("Test ...", "Harness ...", "Co-op ...", "Match ..."; one of yours a test only saved into stays), and the guests' saves in Multiplayer, with yours of the same name put back. Steam Cloud may already have them, uploaded whenever no copy had run for a few seconds, and drops a file only in a sync after it's gone; otherwise Steam puts it back the next time it syncs in full (a restart, say). The last copy's own sync, a few seconds after it closes, usually comes after the saves went; when it doesn't, the run starts and closes one more copy for another, and says so if Steam doesn't sync (offline). The two copies share a Steam account, so a matchmade game can't be played through: scenarios stop at the two finding each other.

Footguns the runner guards against (a run refuses to start when a mod's code changed after its installed DLL, so it never tests an older build than the code, `--no-build` included; one lock at `$TMPDIR/bb-run-lock` with a first-in first-out queue, builds that skip the Mods install while the lock is held unless `BB_HOLDS_LOCK=1`, a per-run results folder `$BB_TEST_DIR/runs/`, `BB_SCENARIO_TIMEOUT`, load errors that fail `start_match` at once): see the Footguns section of Timber Empires' `Tools/Tests/README.md`.
